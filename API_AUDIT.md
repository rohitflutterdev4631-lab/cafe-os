## 1. REST API Standards & Response Format

All API endpoints follow a unified response structure:
- **Success Response:**
  ```json
  { "success": true, "data": { ... } }
  ```
- **Error Response:**
  ```json
  { "error": "Human-readable error description", "details": ... }
  ```

### HTTP Status Code Compliance
- `200 OK`: Successful retrieval or update.
- `201 Created`: Resource successfully provisioned (orders, categories, dishes).
- `400 Bad Request`: Validation failure (missing required fields, sold-out items, below minimum order).
- `401 Unauthorized`: Missing or invalid session JWT cookie.
- `403 Forbidden`: Authenticated user lacks role permissions for the requested resource.
- `404 Not Found`: Resource or cafe slug does not exist.
- `500 Internal Server Error`: Unhandled server exception with sanitized error output.

## 2. API Security & Validation Audit

| Endpoint Group | Auth Check | Tenant Isolation | Validation Engine | Idempotency |
| :--- | :--- | :--- | :--- | :--- |
| **Auth APIs** (`/api/v1/auth/*`) | Public (Login/Register) / JWT (`/me`) | Multi-tenant user mapping | Email regex, password length | N/A |
| **Admin APIs** (`/api/v1/admin/*`) | Strict `SUPER_ADMIN` check | Global scope | Schema validation | Supported |
| **Tenant APIs** (`/api/v1/categories`, `/orders`, etc.) | `CAFE_OWNER` / `CAFE_MANAGER` | Enforced via `session.cafeId` | Field types, presence | Supported |
| **Kitchen APIs** (`/api/v1/orders/[id]`) | `KITCHEN_STAFF` / `CAFE_OWNER` | Bound to station `cafeId` | Status enum check | Supported |
| **Customer Order APIs** (`/api/v1/public/c/[slug]/orders`) | Public (Table/Dine-In) | Bound to cafe slug & table | Full DB price recalculation | `idempotencyKey` supported |
| **Public Order Tracking** (`/api/v1/public/orders/[num]`) | Public with PII Masking | Bound to cafe | Phone verification check | N/A |
| **AI Menu Importer** (`/api/v1/menu-imports/*`) | `CAFE_OWNER` / `SUPER_ADMIN` | Scoped to active tenant | Magic-byte file validation | Atomic transactions |

## 3. Idempotency & Duplicate Order Defense

In `src/app/api/v1/public/c/[slug]/orders/route.ts`:
- Accepts optional `idempotencyKey` (UUID generated by client on checkout submission).
- If network disconnection causes the client to retry checkout with the same `idempotencyKey`, the server returns the existing order instead of double-charging or creating duplicate kitchen tickets.
